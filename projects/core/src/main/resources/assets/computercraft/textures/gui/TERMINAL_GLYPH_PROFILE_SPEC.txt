CC: Tweaked Terminal Glyph Profiles
==================================

Overview
--------

ComputerCraft is fundamentally an English-first terminal environment.
This fork adds a way to customise which glyph shapes are used for terminal
input and rendering while preserving the original fixed 256-glyph terminal
model.
This folder contains the core files for that system: profile JSON files and
their matching font PNG images.

More specifically, by preparing a terminal font image containing 256 glyphs of
size 6x9 and a profile JSON which defines which Unicode characters map to
those glyphs, you can decide which characters are input and displayed within
that 256-glyph limit.
The bundled Japanese katakana files are one sample implementation of this
system.


Files
-----

- term_font.png
  Default ASCII terminal font texture.

- term_font_jp_katakana.png
  Japanese katakana terminal font texture.

- glyph_map_ascii.json
  Default ASCII-only glyph profile.

- glyph_map_jp_katakana.json
  Japanese katakana glyph profile with aliases and IME settings.


Selecting a profile
-------------------

Profiles are selected in ComputerCraft's `computercraft-client.toml` file
using the `terminal_glyph_map` setting.

Example 1 (default value):
  terminal_glyph_map = "computercraft:textures/gui/glyph_map_ascii.json"

Example 2 (bundled Japanese katakana profile):
  terminal_glyph_map = "computercraft:textures/gui/glyph_map_jp_katakana.json"

If this setting is omitted or invalid, CC falls back to the default ASCII
setting from Example 1:

  computercraft:textures/gui/glyph_map_ascii.json


Adding your own profile
-----------------------

For quick local testing, place your JSON and PNG files directly into the mod
JAR under:

  assets/computercraft/textures/gui/

For example:

  assets/computercraft/textures/gui/glyph_map_hiragana.json
  assets/computercraft/textures/gui/term_font_hiragana.png

Then configure the same paths in these two places:

- the `terminal_glyph_map` setting in ComputerCraft's
  `computercraft-client.toml` file:
  `computercraft:textures/gui/glyph_map_hiragana.json`
- the `font` field inside the profile JSON:
  `computercraft:textures/gui/term_font_hiragana.png`

On Windows, tools such as 7-Zip can open a JAR directly and let you add files
without fully extracting the archive.


glyph profile JSON file format
------------------------------

Each glyph profile JSON may define:

- schema
  JSON structure version.

- name
  Human-readable profile name.

- font
  Font texture resource used by terminal rendering. This should point to the
  matching PNG for the profile, using a normal resource location.

- fallbackGlyph
  Glyph index used for unsupported input, usually `63` (`?`).

- imeEnterDelay
  Delay in milliseconds for IME Enter handling.
  Use `0` to disable delayed Enter handling.

- map
  Unicode BMP code point mappings in `U+XXXX` form (`U+0000` to `U+FFFF`).

Example entry:

  "U+30A2": { "glyph": 128, "char": "ア" }

The optional `char` field is only for readability and validation.


glyph PNG file format
---------------------

The terminal renderer expects the following layout. This is part of the
original CC behaviour:

- texture size: 256x256
- glyph grid: 16x16
- glyph body size: 6x9
- cell step: 8x11
- glyph 0 origin: x=1, y=1

texture lookup formula:

  column = glyph % 16
  row    = glyph / 16
  x = 1 + column * 8
  y = 1 + row * 11

Only the 6x9 glyph area inside each cell is sampled.


Editing notes:

- only edit areas where glyphs are already drawn; do not touch the empty areas
- do not modify the narrow reserved area at the far right edge of the image
- keep the whole image at 256x256
- preserve alpha when exporting
- do not flatten the image to opaque black and white

If a PNG edited in a bitmap image editor picks up unwanted extra information
from its save/export settings, ImageMagick may help rewrite it into a clean
PNG:

  magick out.png PNG32:term_font.png

If needed, you can also check whether alpha is still present:

  sips -g hasAlpha term_font.png


Normalisation policy
--------------------

Built-in language-specific normalisation is intentionally not used.

If multiple Unicode characters should map to the same terminal glyph, define
them explicitly in the JSON `map`. This includes compatibility forms such as
full-width ASCII, katakana variants, and similar aliases.


Where mapping is applied
------------------------

The glyph profile's `map` is currently applied to:

- IME/direct character input in terminal widgets
- Paste input in terminal widgets

The map is not currently re-applied to existing terminal glyph data already
stored in the terminal. Existing terminal contents are rendered as their raw
0..255 glyph codes using the currently selected font texture.

In practice this means:

- input path: Unicode character -> glyph profile map -> 0..255 glyph code
- render path: existing 0..255 glyph code -> selected font texture cell


Known IME limitation
--------------------

On some IME/OS combinations, confirming a conversion with Enter may still
produce an extra newline before the committed characters arrive.

The current delayed-Enter handling can suppress some follow-up Enter presses,
but it cannot reliably distinguish the very first IME confirmation Enter from
a real terminal Enter.

This has been observed on macOS with Japanese IME. Treat IME direct input as
experimental/incomplete for now.
